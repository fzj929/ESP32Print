# 设备管理网站开发计划（讨论稿）

状态：需求讨论稿，未作为最终实施或安全验收基线。**已确定网站部署在公网服务器；本地终端同时连接运营商蜂窝网络和目标板卡 Wi-Fi，由浏览器经两条链路转发作业。**本文承接[板卡开发计划](开发计划.md)，不把当前工程测试固件尚未完成的量产功能视为已具备。

## 1. 目标与边界

构建一个多用户设备与打印作业管理网站。普通用户只管理自己绑定的板卡和作业；平台管理员可查看全部用户、板卡和作业。用户可上传**目标打印机驱动已经生成的逐页 PRN 文件**，选定文件/作业与板卡，在板卡可达时按页发送。网站记录状态、最近通讯时间、操作审计与凭据版本。

约定技术栈：ASP.NET Core Web API（C# / .NET 8）、MySQL、Vue 3 + TypeScript。二进制 PRN 页面放对象存储或受控文件存储；MySQL 只保存元数据、状态和密文引用，不存大文件 BLOB。开发时保留升级到后续 .NET LTS 版本的空间；[微软生命周期](https://learn.microsoft.com/en-us/lifecycle/products/microsoft-net-and-net-core)显示 .NET 8 支持至 **2026-11-10**，正式交付前必须明确运行时升级计划。

非目标：网站不生成通用 PRN、不把任意多页 PRN 自动切页、不保证 `usb_delivered` 等于纸张出纸完成，也不承诺网页自动切换手机/电脑的 Wi-Fi 网络。

## 2. 必须先验证的连接方案

当前 ESP32 只有 SoftAP，所有板卡在各自热点内都使用 `192.168.188.1`。公网服务器不能凭这个地址区分并直连不同板卡；只有**已连接目标板卡热点**的手机/电脑，或专用现场网关，才有到该地址的路由。多个板卡的同一个 IP 不构成服务器侧的多个公网地址。

已确定按以下两条链路设计：

```text
管理/文件链路：Vue 浏览器 ⇄ 运营商蜂窝网络 ⇄ HTTPS 网站 API ⇄ MySQL + PRN 文件存储
本地打印链路：Vue 浏览器 ⇄ 当前连接的板卡 Wi-Fi ⇄ http://192.168.188.1 ⇄ USB 打印机
```

浏览器直连要求用户**主动连接目标板卡热点**，并且打印期间经蜂窝网络逐页访问公网网站。这里把双网络作为产品前提，但仍须在目标终端（手机、平板或具备蜂窝网络的电脑）和浏览器上确认路由选择：访问公网 API 时实际走蜂窝网络，访问 `192.168.188.1` 时实际走 Wi-Fi，切换网络或锁屏后两者不丢失。第一版不把只有单个 Wi-Fi、没有蜂窝数据的电脑作为保证支持的打印终端。若目标终端不能稳定双链路，当前“网站取页—浏览器转发”流程不可用；须先决定受控离线暂存方案或调整组网，不把失败推给用户。网站必须在打印前完成真实设备验证：从板卡读取 `device_id` 与打印机指纹，与用户选中的记录比对；绝不能仅因 `192.168.188.1` 有响应就认定连对了板子。

从 HTTPS 网站对本地 HTTP 板卡发起 `fetch`，不同浏览器有不同限制。Chrome 的[本地网络访问机制](https://developer.chrome.com/blog/local-network-access)需要安全上下文和用户许可，并对已识别的本地地址提供混合内容例外；这不能替代普通跨源读取所需的 CORS 支持，也不能假定 Safari/Firefox 行为相同。当前固件没有 CORS/OPTIONS 支持，故**不得先做整个网站再期待页面自然可以调用板卡**。阶段 0 必须使用目标终端和浏览器做登录、状态查询、2 MiB 上传的端到端实验。

本轮选择浏览器直连为主路径，**不在第一版假定存在现场网关**。如浏览器直连或蜂窝/Wi-Fi 并行路由验证失败，必须回到需求决策，评估现场网关/本地助手或板卡 AP+STA + 出站 HTTPS/MQTT；不能只增加 CORS 代码就宣称公网打印可用。单个 Wi-Fi 接口也不能同时驻留多个互不相同的板卡热点；用户一次只连接并操作一块板子。

## 3. 用户、板卡和权限

角色：`user`、`platform_admin`。每块板卡有唯一 `device_id` 与一个当前所有者；管理员可查看全部记录、禁用或转移设备，但默认**无权读取用户的明文 Wi-Fi/板卡管理密码**。后续共享板卡可通过独立的 `device_memberships` 授权，不靠共享账号。所有读写 API 在数据库查询层按所有者/授权关系过滤，不能只在 Vue 页面隐藏按钮。

板卡新增流程：用户登录 → 输入/扫描设备编号 → 提交制造时给出的每机绑定证明或恢复码 challenge → 服务端验证编号未被占用、证明有效、设备状态允许绑定 → 创建归属关系。**仅输入一个编号不能证明占有板卡。** 删除采用软删除/解绑，保留审计、历史作业和编号占用记录；解绑时吊销访问授权及本地代理令牌，是否允许重新绑定由设备策略决定。

当前固件仅能**读取**预留 eFuse 编号格式，量产写入、每机恢复码 claim 和设备证书尚未完成，因此真实设备注册必须依赖后续固件/制造流程；在阶段 0 可使用明确标记的测试设备，不得把测试绑定方式上线。

## 4. 凭据与设备管理

- `GET /api/v1/devices/{id}/wifi-credentials`：仅所有者，经近期重新验证身份后返回该板卡当前已知的 SSID/密码；响应 `Cache-Control: no-store`，记录“谁、何时、为什么查看”。
- `GET /api/v1/devices/{id}/local-credentials`：同样受限；当前板卡登录接口只有**管理密码**，没有用户名字段，不应虚构“板卡账号”。返回凭据版本与最后确认时间。正常打印不应要求管理员反复手动查看密码。
- 恢复密钥：优先制造时一次性展示/交付。若业务明确要求网站可找回，则只能由独立密钥管理服务加密托管，启用二次验证、限频、审计与可撤销/轮换；管理员“查看所有板卡”不自动等于可查看恢复密钥。
- 修改板卡 Wi-Fi 或管理密码时，必须先证明用户在本地连对板子。浏览器/现场网关调用板卡成功后，再更新服务器的加密凭据及版本；断连使结果不确定时标记 `pending_reconciliation`，重新探测核对，不盲目重试。

Wi-Fi 密码、板卡管理密码和可找回的恢复密钥不得以明文写入 MySQL、日志、浏览器本地存储或分析系统。数据库只存密文、密钥引用与版本；密钥放在独立 KMS/机密服务。HTTPS 保护网站链路，但当前板卡本地 HTTP 仍会明文传输板卡密码与 PRN；这是正式产品安全验收阻断项，需由板卡 TLS 或可信现场代理解决。

## 5. 作业与文件模型

用户上传的最小单位是“一页、一个由目标驱动生成的 PRN”。创建作业时给出 `device_id`、预期打印机指纹、总页数和文件清单；每页存储 `page_no`、大小、SHA-256、存储键及原始文件名。严格限制每页不超过板卡的 2 MiB 上限，页面必须从 1 连续编号，缺页作业不能进入可打印状态。单个多页 PRN **不自动拆分**；若以后支持，需针对具体 PDL/驱动证明分页边界可靠。

文件对象默认仅上传者和授权管理员可访问；用户之间不能凭猜测 ID 下载。文件列表 API 返回所属用户、页数、大小、创建时间、目标打印机/驱动描述及状态；单页下载 API 返回原始字节、正确长度和摘要，供浏览器/现场网关转发到板卡。设置用户配额、保留期和删除策略；PRN 可能含文档隐私，不输出内容到日志。

服务端作业状态至少区分：`draft` → `ready` → `dispatching` → `usb_delivered`；另外有 `failed_before_usb`、`failed_unknown`、`cancelled`。每页单独记录状态、板卡会话 ID、请求幂等键、最后一次确认的字节摘要与时间。板卡只允许一个打印会话；服务端也对同一板卡做互斥调度。出现 `failed_unknown` 时停住并要求人工核对纸张，不能自动重发。

## 6. 网站 API 草案

所有 `/api/v1` 接口要求网站用户认证，按设备/作业归属授权；管理员查询必须指定审计范围。统一返回 `request_id`、错误码与服务器 UTC 时间；分页列表需稳定排序。

| 能力 | API 草案 | 主要约束 |
|---|---|---|
| 用户 | `POST /auth/login`、`POST /auth/logout`、`GET /me`；管理员 `/admin/users` | MFA/限频/会话吊销；后台禁用用户 |
| 板卡列表与增删 | `GET/POST /devices`、`GET/DELETE /devices/{id}` | 新增需占有证明；删除为软删除 |
| 板卡凭据 | `GET /devices/{id}/wifi-credentials`、`GET /devices/{id}/local-credentials` | 所有者 + 近期再认证 + 审计 + 不缓存 |
| 恢复密钥 | `POST /devices/{id}/recovery-claims`、`POST /devices/{id}/recovery-rotations` | 一次性或受控托管；不能普通列表返回 |
| 板卡配置 | `PUT /devices/{id}/wifi`、`PUT /devices/{id}/local-password` | 本地在场验证、板卡确认、版本化、失败待核对 |
| 状态查询 | `GET /devices/{id}/status`、`GET /devices/{id}/printer` | 返回状态来源、采样时间、可信级别与过期标识 |
| 文件 | `POST /files`、`GET /files`、`GET /files/{id}`、`GET /files/{id}/pages/{n}`、`DELETE /files/{id}` | 逐页上传/下载；属主校验；大小和摘要校验 |
| 作业 | `POST /jobs`、`GET /jobs`、`GET /jobs/{id}`、`POST /jobs/{id}/dispatch`、`POST /jobs/{id}/cancel` | 作业归属、板卡互斥、每页结果追踪 |
| 设备信息上报 | `POST /device-reports` | **仅设备签名或可信现场代理**；包含编号、固件版本、打印机指纹 |
| 状态上报 | `POST /device-reports/status`、`POST /device-reports/printer-status` | 防重放、服务端接收时间、设备采样时间、序号 |
| 管理员 | `GET /admin/devices`、`GET /admin/jobs`、`GET /admin/audit-events` | 全局筛选/分页；敏感凭据不默认展示 |

上报接口不接受“普通登录用户自己声称某板在线”的数据作为可信心跳。浏览器直连阶段可上报 `local_observation`，但界面须标“用户浏览器最近发现”，与设备签名心跳分开。

## 7. 最近通讯时间与在线判定

数据库分别保存 `last_verified_seen_at`（最近通过设备签名/可信代理验证的通讯）、`last_local_observation_at`（浏览器最近发现）、`last_printer_sample_at`、`last_job_contact_at`，均用 UTC。界面显示“上次通讯：相对时间 + 绝对时间 + 来源”；在线状态按可配置阈值和来源计算，过期状态不显示为实时。当前 SoftAP 固件不能主动上报公网，若没有浏览器或现场网关连接，网站**无法持续判断它是否在线**。

## 8. 浏览器本地打印流程

1. 用户登录网站，选择自己有权使用的板卡和已完整上传的逐页作业。
2. 网站提示连接该板卡的 SSID；网页展示目标名称，但不尝试自动改动操作系统 Wi-Fi。
3. 用户触发“发现板卡”；Vue 从 `http://192.168.188.1/` 读取最小身份/状态接口。网络、权限、CORS、身份不符分别报错。
4. 比对不可变 `device_id`、打印机 VID/PID/序列号或 IEEE 1284 信息及作业预期驱动；若编号为空或不匹配，禁止打印。网站先通过授权接口取板卡本地凭据，在内存中登录板卡取得短期 Token；不持久化到浏览器存储。
5. 创建板卡独占会话，声明作业号、总页数和打印机指纹。浏览器逐页从网站取得原始字节，验证 SHA-256 后传到板卡，并校验板卡响应；等待 `usb_delivered` 后才发送下一页。
6. 浏览器把**板卡原始结果**及其验证材料回报网站；断网/页面关闭时停在“待核对”，不假定成功，也不自动重传结果不明的页面。

打印页链路必须逐页在蜂窝网上取文件、在 Wi-Fi 上交给板卡；开始每页前同时探测两条链路。蜂窝网络中断时不应提交下一页；Wi-Fi 中断后先重新查询板卡会话，不能把上传超时直接当作“未打印”。避免依赖长时间后台运行：移动浏览器锁屏或切出页面时应暂停并明确提示恢复步骤。

当前板卡固件返回 `device_id: null`，缺少跨源访问支持，且本地登录仅靠共享管理密码；所以第 3～6 步是**待实现的固件与安全协议工作**，不能用当前固件宣称完成。为降低浏览器持有板卡管理员密码的风险，正式版宜提供按设备/作业范围、短时有效的授权令牌或可信现场代理。

## 9. 数据库与服务划分

建议表：`users`、`user_sessions`、`devices`、`device_memberships`、`device_secret_refs`、`device_bindings`、`printer_snapshots`、`device_reports`、`files`、`file_pages`、`jobs`、`job_pages`、`job_events`、`audit_events`、`outbox_events`。所有外键按属主/设备 ID 建索引；`devices.device_id` 全局唯一，`file_pages(file_id,page_no)`、`job_pages(job_id,page_no)` 唯一。删除设备/文件采用状态迁移，避免破坏历史审计。

ASP.NET Core 项目拆为 API、领域服务、MySQL 持久层、PRN 存储适配器、后台清理/调度 Worker；Vue 页面拆为用户登录、我的板卡、板卡详情/凭据、文件库、作业列表/详情、现场打印控制台、管理员用户/板卡/作业/审计。数据库迁移、备份恢复、对象存储生命周期与密钥轮换纳入部署脚本。需要定义单用户/单设备并发和文件配额，不仅依赖 ESP32 的 2 MiB 单页限制。

## 10. 分阶段实施与验收

**阶段 0：网络与浏览器可行性（先做）**。用实际 ESP32、目标打印机、具备蜂窝网络的目标终端及浏览器，验证蜂窝网络与板卡 Wi-Fi 同时可用、HTTPS 网站和 `192.168.188.1` 同时可达且分别走正确出口、跨源许可、Bearer 请求、2 MiB 上传、Wi-Fi 切换后的重连、锁屏/切后台后的行为；记录失败矩阵。若目标设备不满足双链路，不进入大规模页面开发，先确认受控离线暂存是否可接受或重新决定组网。

**阶段 1：用户与资产底座**。建立 .NET 8 API、Vue 3、MySQL、用户登录/角色/归属过滤、管理员视图、审计、设备绑定证明、设备软删除与密钥托管。验收：跨用户越权测试、绑定抢占测试、密钥访问审计通过。

**阶段 2：文件与作业库**。逐页 PRN 上传、大小/SHA-256、文件列表/页数/单页读取、作业状态机、配额与清理。验收：缺页/越权/重复提交/超限/断点失败均有确定结果。

**阶段 3：板卡协议适配**。板卡不可变 ID/制造绑定、CORS/OPTIONS 精确来源策略、最小发现接口、跨源本地登录/授权、状态回报签名、打印页幂等与故障核对。验收：错板阻断、并发互斥、断线不重印、可信上报可验签。

**阶段 4：端到端打印**。浏览器直连或现场网关实现顺序发页、心跳、进度、取消和未知结果处理；管理员能跨用户查询但不能默认查看秘密。验收：多用户、多板、多打印机、网页关闭、Wi-Fi 断线、USB 故障、服务器重启的测试矩阵。

**阶段 5：量产安全与运维**。HTTPS/证书或可信代理、设备密钥轮换、安全启动/加密、签名 OTA、监控告警、备份恢复、数据保留、渗透测试、目标浏览器回归及 .NET 运行时升级决策。未通过前按工程测试环境交付，不标记为正式产品。

## 11. 本轮需要确认的决策

1. 已确认：网站部署在公网；本地终端同时连接蜂窝网络与板卡 Wi-Fi；浏览器本地连接板卡热点；第一版不依赖现场网关。
2. 待确认：目标终端是手机、平板还是蜂窝联网电脑？操作系统、浏览器及最低版本是什么？双网络路由和锁屏行为仍需阶段 0 实测。
3. 每个用户只拥有自己的板卡，还是需要团队共享/转移/租借？管理员是否只看元数据，还是要有紧急读取秘密的授权流程？
4. 每页 PRN 由用户单独上传，还是已有服务器端驱动服务负责按页生成？若上传“整份 PRN”，必须先提供明确的分页格式约束。
5. 是否接受“USB 字节已送达”作为第一版成功状态？若要求确认实际出纸，需指定打印机型号与可用的反馈协议。
6. 设备上报公网需要新的联网模式或现场网关；若第一版仅浏览器直连，是否接受“最近通讯”只在有人打开网站并连接板卡时更新？

下一轮建议先定第 2、6 项，再冻结阶段 0 验收矩阵；它们会直接决定逐页文件链路和“最近通讯时间”的可信含义。
